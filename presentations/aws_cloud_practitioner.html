☁️ Module 1

Introduction to Cloud Computing

☁️ What Is Cloud Computing?

The on-demand delivery of IT resources over the internet with pay-as-you-go pricing.

  • Instead of buying and maintaining physical data centers and servers, you rent compute, storage, databases and more from a cloud vendor (AWS, Azure, Google Cloud …)
  • Resources are provisioned in minutes via a web console, command line or API — and released just as fast
  • Geographically distributed — deploy close to your users anywhere in the world

CapEx → OpEx

  • Capital expense: large up-front hardware purchase you must forecast years ahead
  • Operational expense: variable monthly cost that tracks actual usage

NIST's five essential characteristics

  • On-demand self-service — provision without human interaction with the provider
  • Broad network access — available over the network from standard clients
  • Resource pooling — multi-tenant model; physical resources are shared and isolated by virtualization
  • Rapid elasticity — scale out and in quickly, appearing unlimited
  • Measured service — usage is metered, monitored and billed

📝 Exam tip: Know these five characteristics — questions often describe one and ask you to name it.

💡 Benefits of Cloud Computing — The Six Advantages

1. Trade fixed expense for variable expensePay only for what you consume instead of investing in data centers before you know how you'll use them.
2. Benefit from massive economies of scaleAWS aggregates usage from millions of customers and passes lower per-unit costs on.
3. Stop guessing capacityScale up or down in minutes — no more over-provisioning "just in case" or under-provisioning and losing customers.
4. Increase speed and agilityNew resources are a click away; the cost of experimenting drops to nearly zero.
5. Stop spending money running data centersFocus on your customers, not on racking, stacking and powering servers.
6. Go global in minutesDeploy your application in multiple Regions around the world with a few clicks.

Why AWS specifically?

  • Market leader with the broadest and deepest set of services (200+)
  • Largest global footprint; mature security and compliance programs
  • Everything is an API — automate all of it

📝 Exam tip: The six advantages come straight from the AWS "Overview of Amazon Web Services" whitepaper and appear frequently in Domain 1 questions.

🏢 Types of Cloud Computing (Deployment Models)

Public cloudAll resources run on a provider's shared infrastructure (AWS). Fastest to start, pay-as-you-go, provider handles the hardware.
Private cloudCloud-style virtualization and self-service inside your own data center (VMware, OpenStack). You own capacity, patching and the CapEx.
Hybrid cloudOn-premises connected to the public cloud — VPN or Direct Connect, Storage Gateway, AWS Outposts. Common during migrations and for data-residency constraints.
Multi-cloudUsing two or more public clouds. Motivations: avoiding lock-in, best-of-breed services, acquisitions. Cost: more complexity and skills to maintain.

Migration strategies you will hear about (the "6 Rs")

  • Rehost (lift and shift) · Replatform (lift, tinker and shift) · Repurchase (move to SaaS)
  • Refactor (re-architect for cloud) · Retire · Retain

AWS hybrid tools: AWS Outposts (AWS racks in your building), Storage Gateway, Direct Connect, Site-to-Site VPN, Systems Manager for on-prem servers.

🗺️ Primer: Where Do Things Live in AWS?

You will need these three terms for every lab today. Module 3 covers the global infrastructure in depth.

  • Region — a geographic area with its own independent set of AWS resources, e.g. us-east-2 (Ohio). You have been assigned a Region for today — every lab runs there.
  • Availability Zone (AZ) — one or more isolated data centers inside a Region (named <region>a, b, c …). Spreading across AZs is how you survive a data-center failure.
  • Edge location — hundreds of small sites worldwide used by CloudFront and Route 53 to serve content close to users.

Scope matters: IAM and Route 53 are global. VPC, EC2, RDS and most others are Regional — pick the wrong Region in the console and your resources "disappear".

Three ways to talk to AWS

  • Management Console — web UI; best for learning and one-off tasks
  • AWS CLI — aws s3 ls; scriptable. CloudShell gives you a browser terminal with the CLI pre-installed
  • SDKs & Infrastructure as Code — boto3, JavaScript, Java …; CloudFormation, CDK, Terraform
Console --+ CLI --+--> HTTPS --> AWS API --> IAM authenticates SDK/IaC --+ and authorizes --> service acts

📝 Exam tip: Console = password (+ MFA). CLI/SDK = access key ID + secret access key — or better, an IAM role.

🔐 Module 2A

Security, Identity & Compliance — IAM and KMS

🤝 The Shared Responsibility Model

🟧 AWS: security OF the cloud

  • Physical security of data centers, hardware and the global network
  • Virtualization layer (hypervisor) and host operating systems
  • The infrastructure under managed services (RDS, Lambda, S3 …)
  • Compliance of the infrastructure (SOC, ISO 27001, PCI DSS, HIPAA eligibility …) — evidence in AWS Artifact

🟦 Customer: security IN the cloud

  • Your data — classification, encryption at rest and in transit
  • IAM users, groups, roles, permissions and MFA
  • Guest OS patching and firewall configuration on EC2
  • Application code, security groups, network ACLs, VPC design

Responsibility shifts with the service: on EC2 you patch the OS; on RDS AWS patches the engine but you control encryption, users and backup retention; on Lambda you own only your code and its permissions.

📝 Exam tip: "Who patches the OS on an EC2 instance?" → customer. "Who disposes of failed disks?" → AWS. Encryption is a shared control: AWS provides the capability, you turn it on.

🪪 AWS Identity and Access Management (IAM)

IAM controls who (authentication) can do what (authorization) on which resources.

  • Global service — not tied to a Region; free of charge
  • Integrated with every AWS service; managed via console, CLI or SDK

The root user

  • Created with the account; signs in with the account email; unrestricted access that no policy can limit
  • Use it only for tasks that require it (close the account, change support plan, some billing settings)
  • Enable MFA on root, lock the credentials away, create IAM identities for daily work
EntityWhat it is
UserA person or application with long-term credentials (password and/or access keys)
GroupA collection of users; attach policies once for everyone. Not nestable; a user may be in several groups
RoleAn identity with temporary credentials that a trusted entity assumes — an EC2 instance, a Lambda function, a user in another account, a federated user
PolicyA JSON document that allows or denies actions on resources; attached to users, groups or roles

📝 Exam tip: An application on EC2 needs to read S3 → attach an IAM role to the instance. Never store access keys on the instance. (You create this role in Lab 1 and use it in Labs 3 and 5.)

📜 IAM Policies and Least Privilege

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [ "s3:ListBucket", "s3:GetObject" ],
      "Resource": [
        "arn:aws:s3:::user7-bucket-4821",
        "arn:aws:s3:::user7-bucket-4821/*"
      ]
    }
  ]
}
  • Effect — Allow or Deny · Action — the API calls (service:Operation)
  • Resource — the ARN(s) it applies to · Condition (optional) — e.g. require MFA, restrict source IP

Evaluation rules

  • Everything is implicitly denied by default
  • An explicit Allow grants access …
  • … but an explicit Deny always wins

Policy types

  • AWS managed — maintained by AWS (AmazonS3ReadOnlyAccess, AdministratorAccess)
  • Customer managed — you write and reuse across identities
  • Inline — embedded in one identity

Principle of least privilege: grant only what the job needs. Start narrow; widen when a real need appears.

🔑 Credentials, MFA and Key Management Service

Credentials

  • Password → console (account ID or alias + user name)
  • Access key ID + secret → CLI, SDK, API
  • Temporary credentials (STS) → issued when a role is assumed; expire automatically
  • Password policy — length, complexity, expiry, reuse

Multi-Factor Authentication

  • Something you know + something you have
  • Virtual (authenticator app), FIDO2 security key, hardware TOTP token
  • Root first, then every human user

Beyond IAM users

  • IAM Identity Center — single sign-on across many accounts; federate Active Directory, Okta, Entra ID (SAML 2.0)
  • Amazon Cognito — sign-up / sign-in for your application's end users, including social logins

📝 Workforce → Identity Center. App customers → Cognito. Machines → IAM roles.

AWS Key Management Service (KMS)

  • Create, rotate, disable and audit encryption keys; keys are Regional and identified by ARN
  • Integrated with S3, EBS, RDS, DynamoDB, Lambda, Secrets Manager and 100+ services — encryption at rest is a checkbox
  • Every use of a key is logged in CloudTrail
  • AWS managed keys (free, per service) vs customer managed keys (you control policy and rotation)
  • AWS CloudHSM — dedicated, single-tenant hardware security modules when regulations require it

S3 encryption options: SSE-S3 (S3 keys), SSE-KMS (KMS keys), SSE-C (your keys). In transit: TLS via AWS Certificate Manager.

🕸️ Module 2B

Networking & Content Delivery — VPC, Security Groups & NACLs, Route 53, CloudFront

🏠 Amazon VPC: Your Private Network in AWS

A logically isolated virtual network where you launch EC2 instances, RDS databases and other resources.

  • Lives in one Region and spans all its AZs
  • You choose a private IPv4 range in CIDR notation, e.g. 10.0.0.0/16 (65,536 addresses; /16 largest, /28 smallest); it cannot be changed later
  • Every Region has a default VPC so you can launch instances immediately — real workloads get custom VPCs

Subnets

  • A slice of the VPC range that lives in exactly one AZ (e.g. 10.0.1.0/24); AWS reserves 5 IPs per subnet
  • Public subnet — its route table sends 0.0.0.0/0 to an Internet Gateway
  • Private subnet — no internet route; reaches out through a NAT Gateway
ComponentPurpose
Internet GatewayTwo-way internet access for public subnets; one per VPC
Route tableDestination → target rules for subnet traffic; the local route is always present
NAT GatewayOutbound-only internet for private subnets
Security groupInstance-level firewall
Network ACLSubnet-level firewall
VPC Flow LogsCapture IP traffic metadata for troubleshooting and security
Elastic IPA static public IPv4 address you own and can re-assign
VPC endpointPrivate path to S3, DynamoDB and other services — no IGW needed

  • The database security group trusts the web security group, not an IP address — a core AWS pattern

🚧 Security Groups vs Network ACLs

Security GroupNetwork ACL
Applies toInstance / network interfaceSubnet (every instance in it)
RulesAllow only — anything not allowed is deniedAllow and Deny; numbered; evaluated lowest number first; * rule denies at the end
StateStateful — return traffic is automatically allowedStateless — you must allow inbound and outbound explicitly (ephemeral ports 1024–65535!)
DefaultsDefault SG: all outbound, inbound only from itself. New SG: no inboundDefault NACL: allow everything. New NACL: deny everything
Typical use"Web servers accept 80/443 from anywhere; DB accepts 3306 only from the web SG"Block a malicious IP range for a whole subnet; coarse subnet-level guardrails

Security group rule anatomy

  • Type / protocol — HTTP (TCP 80), SSH (TCP 22), MySQL (TCP 3306), All ICMP …
  • Source — a CIDR (0.0.0.0/0 = anywhere, 203.0.113.5/32 = one host) or another security group ID

📝 Exam tip: "Stateful", "instance level" → security group. "Stateless", "subnet level", "deny rule" → network ACL. Both are your responsibility.

🌐 Route 53, CloudFront and Hybrid Connectivity

📡 Amazon Route 53 — DNS

  • Highly available, scalable DNS with a 100% availability SLA; also registers domains
  • Hosted zones (public or private) hold records: A, AAAA, CNAME, MX, TXT, Alias (points at ELB, CloudFront, S3)
  • Routing policies: simple · weighted (blue/green) · latency-based · failover (with health checks) · geolocation · geoproximity · multi-value

⚡ Amazon CloudFront — CDN

  • Caches content at 600+ edge locations; origin can be S3, ELB, EC2 or any HTTP server
  • Lower latency, lower origin load, lower data-transfer cost; HTTPS at the edge with free ACM certificates
  • Integrates with Shield and WAF for edge protection; signed URLs for private content

🔗 Connecting networks

ServiceUse when
VPC PeeringTwo VPCs need private routing (not transitive)
Transit GatewayMany VPCs and sites — hub-and-spoke
Site-to-Site VPNEncrypted tunnel to on-premises over the internet; minutes to set up
Direct ConnectDedicated private fiber — consistent bandwidth and latency; weeks to provision
VPC EndpointsReach S3/DynamoDB/other services without an IGW (PrivateLink)
Global AcceleratorStatic anycast IPs routing users over the AWS backbone (Module 3)

📝 "Private, dedicated, consistent" → Direct Connect. "Quick, encrypted, over the internet" → VPN. "Cache static content near users" → CloudFront. "DNS failover" → Route 53 health checks.

Compute — Amazon EC2

🖥️ Amazon Elastic Compute Cloud (EC2)

Resizable virtual servers in the cloud — the IaaS workhorse of AWS. Launch in minutes, pay per second, stop or terminate any time.

What you choose at launch

  • AMI (Amazon Machine Image) — the OS and pre-installed software template: Amazon Linux 2023, Ubuntu, Windows Server, Marketplace images, or your own custom AMIs
  • Instance type — the CPU / memory / storage / network profile
  • Key pair — public/private key for SSH (Linux) or password decryption (Windows); AWS keeps the public half, you download the .pem once
  • Network — VPC, subnet, public IP, security group(s)
  • Storage — root EBS volume size/type, extra volumes
  • IAM role (instance profile), user data script, tags

Instance type families

FamilyOptimized forExamples
General purposeBalanced; web servers, dev/testt3, t4g (burstable), m6i, m7g
Compute optimizedHigh CPU; batch, gaming, HPCc6i, c7g
Memory optimizedLarge in-memory datasets; SAP, cachesr6i, x2, u-
Storage optimizedHigh local disk IOPS; NoSQL, data warehousesi4i, d3
AcceleratedGPUs / ML chipsp5, g5, inf2, trn1

Naming: t3.micro = family t, generation 3, size micro. Graviton (ARM) types end in g and cost ~20% less.

Instance lifecycle: pending → running → stopping → stopped → (start again) … → terminated. Stopping keeps the EBS root volume; terminating deletes it by default. Public IPs change on stop/start unless you use an Elastic IP.

🔌 Connecting To and Securing an Instance

Ways in

  • EC2 Instance Connect — browser-based SSH from the console; no key file to manage (Lab 3)
  • SSH with your key pair — ssh -i userN-key.pem ec2-user@<public-ip>
  • Session Manager (Systems Manager) — no open port 22 at all; audited sessions; the production best practice
  • RDP — Windows instances, port 3389

Root vs instance store

  • EBS-backed (the norm) — persistent network volume; survives stop/start; snapshots to S3
  • Instance store — physically attached, very fast, ephemeral — data is lost on stop or termination

Security checklist for a web server

  • Security group: only the ports you serve (80/443); SSH restricted to your IP or removed in favor of Session Manager
  • IAM role instead of access keys on the box
  • Patch the OS — it is your side of the Shared Responsibility Model (Systems Manager Patch Manager helps)
  • Encrypt EBS volumes (KMS) — one checkbox, no performance penalty
  • Tags: Name, Owner, Environment, CostCenter — used for cost allocation and IAM conditions
  • Use IMDSv2 (token-based instance metadata) — the default on Amazon Linux 2023

📝 Exam tip: "Data lost when instance stops" → instance store. "Connect with no inbound ports open" → Session Manager. "Static public IP that survives stop/start" → Elastic IP.

🚀 Deploying Applications on EC2

Three ways to get software onto an instance

  • Manually — SSH in, install packages, copy files. Fine for learning; does not scale and drifts over time
  • User data — a shell script that runs once at first boot. Installs and configures automatically; the same script gives you identical servers every time
  • Custom AMI — bake the configured instance into an image, then launch copies in seconds. Combine with user data for the last-mile config
#!/bin/bash
dnf install -y httpd
systemctl enable --now httpd
echo "<h1>Hello from $(hostname -f)</h1>" \
  > /var/www/html/index.html

From one server to a fleet

  • Elastic Load Balancing — distributes traffic across instances in multiple AZs and health-checks them. Application LB (HTTP/HTTPS, path routing) · Network LB (TCP/UDP, ultra-low latency, static IP) · Gateway LB (third-party appliances)
  • Auto Scaling group — launches from a launch template (AMI + type + user data), keeps the desired count healthy, scales on CloudWatch metrics (Module 4)
  • AWS Elastic Beanstalk — upload code; it provisions EC2, ELB, Auto Scaling and monitoring for you (PaaS)
  • Containers — Amazon ECS / EKS, with Fargate to run them serverless
  • AWS CodeDeploy / CodePipeline — automated CI/CD onto EC2, Lambda or ECS

📝 Exam tip: "Just deploy my code, manage the infrastructure for me" → Elastic Beanstalk. "Layer 7 path-based routing" → ALB. "Run containers without managing servers" → Fargate.

Storage — Amazon S3 and Amazon EBS

🪣 Amazon Simple Storage Service (S3)

Durable, virtually unlimited object storage accessed over HTTPS. Not a file system — you PUT and GET whole objects.

  • Bucket — a container with a globally unique name, created in one Region (data never leaves it unless you copy it)
  • Object — data (0 bytes – 5 TB) + metadata, identified by a key such as images/2026/logo.png (folders are a display convention)
  • 11 nines durability (99.999999999%) — replicated across ≥ 3 AZs automatically
  • Strong read-after-write consistency for all operations
  • Pay for storage used, requests, and data transfer out; unlimited scale

Common uses

  • Backup and archive · data lakes · static website hosting · media storage · log storage · software distribution · disaster recovery

Features you will use in Lab 5

  • Versioning — keep every version; recover from overwrites and deletes. Once enabled it can only be suspended
  • Static website hosting — serve HTML/CSS/JS directly from the bucket
  • Block Public Access — on by default; you must deliberately turn it off and add a bucket policy to publish
  • Bucket policies (resource-based JSON) · IAM policies · ACLs (legacy) · presigned URLs (time-limited links)
  • Lifecycle rules — transition objects to cheaper classes or expire them after N days
  • Encryption at rest — SSE-S3 is on by default; SSE-KMS for your own keys
  • Event notifications → Lambda, SQS, SNS
  • Replication — same-Region or cross-Region copies

📝 Buckets are Regional; names are global. "Recover an accidentally deleted object" → versioning. "Share a private object for 1 hour" → presigned URL.

📝 Exam tip: "Lowest cost, retrieval in hours is fine" → Glacier Deep Archive. "Unpredictable access" → Intelligent-Tiering. "Shared file system for many EC2 instances" → EFS. "Windows file shares" → FSx for Windows. "Move 80 TB with a slow link" → Snowball Edge.

💾 Amazon Elastic Block Store (EBS)

Persistent block storage volumes for EC2 — the instance sees a hard drive. You saw one in Lab 3 as the root volume.

  • Lives in one AZ; attach to an instance in the same AZ (one volume ↔ one instance, except io2 Multi-Attach)
  • Persists independently of the instance — survives stop/start; detach and re-attach elsewhere
  • Automatically replicated within its AZ
  • Resize or change type while in use
  • Billed for provisioned GB-month even when the instance is stopped — delete unused volumes (Lab 8)

Snapshots

  • Point-in-time, incremental backups stored in S3
  • Copy across AZs and Regions; create volumes or AMIs from them (Lab 4's AMI is an EBS snapshot + metadata)

io2 (provisioned IOPS SSD)Critical databases needing sustained high IOPS and 99.999% durability

sc1 (cold HDD)Infrequently accessed data at the lowest cost

Serverless Compute — AWS Lambda

⚡ AWS Lambda: Run Code Without Servers

Upload a function; AWS runs it in response to events and bills you per millisecond of execution. No instances to size, patch or scale.

  • Languages: Python, Node.js, Java, .NET, Go, Ruby, custom runtimes, container images
  • Scales automatically from zero to thousands of concurrent executions
  • Max 15 minutes per invocation; memory 128 MB – 10 GB (CPU scales with memory)
  • Permissions come from an execution role (IAM role Lambda assumes) — least privilege again
  • Logs and metrics land in CloudWatch automatically
  • Free tier: 1 million requests and 400,000 GB-seconds per month, forever
def lambda_handler(event, context):
    name = event.get("name", "World")
    return {"statusCode": 200,
            "body": f"Hello, {name}!"}

Common triggers

  • S3 — object created → resize image, scan file
  • API Gateway / Function URL — HTTP request → serverless API
  • EventBridge — schedule (cron) or AWS events → nightly cleanup, react to instance state change
  • SQS / SNS / DynamoDB Streams / Kinesis — process messages and records
user --> API Gateway --> Lambda --> DynamoDB upload --> S3 event --> Lambda --> S3 (thumbnail) schedule --> EventBridge --> Lambda --> stop idle EC2

The serverless family

  • AWS Fargate — serverless containers for ECS/EKS
  • Amazon API Gateway — managed REST/HTTP/WebSocket APIs
  • Amazon SQS / SNS / EventBridge / Step Functions — decoupling and orchestration
  • Amazon DynamoDB, Aurora Serverless — serverless data stores

Databases — Amazon RDS and Amazon DynamoDB

🗃️ Amazon Relational Database Service (RDS)

Managed relational databases: AWS handles provisioning, patching, backups, replication and failover — you handle schema, queries and users.

  • Engines: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, Db2 and Amazon Aurora
  • Runs on a DB instance class (e.g. db.t3.micro) inside your VPC — reached via a DNS endpoint, protected by a security group
  • Automated backups (1–35 day retention, point-in-time restore) and manual snapshots
  • Multi-AZ — synchronous standby in another AZ; automatic failover for availability
  • Read replicas — asynchronous copies (same or cross-Region) for read scaling
  • Encryption at rest with KMS; TLS in transit; IAM database authentication
  • Scale compute by changing the class; storage autoscaling

Amazon Aurora

  • AWS-built, MySQL- and PostgreSQL-compatible; up to 5× / 3× the throughput
  • Storage auto-grows to 128 TB, replicated 6 ways across 3 AZs, continuous backup to S3
  • Up to 15 read replicas; Aurora Serverless scales capacity automatically

Other database services

  • Amazon Redshift — petabyte data warehouse for analytics (OLAP)
  • Amazon ElastiCache — in-memory Redis / Memcached for sub-millisecond caching
  • Amazon DocumentDB (MongoDB-compatible) · Neptune (graph) · Timestream · QLDB
  • AWS Database Migration Service — migrate on-prem databases with minimal downtime (homogeneous or with Schema Conversion Tool)

📝 Exam tip: "Improve availability" → Multi-AZ. "Offload read traffic" → read replica. "Data warehouse / BI queries" → Redshift. "Cache to reduce DB load" → ElastiCache.

⚡ Amazon DynamoDB — Serverless NoSQL

Fully managed key-value and document database with single-digit-millisecond latency at any scale. No servers, no patching, no capacity planning (on-demand mode).

  • Table → items → attributes; schemaless except the primary key
  • Partition key (required) spreads data across storage; optional sort key orders items within a partition — e.g. Artist + SongTitle
  • Secondary indexes for other query patterns
  • Capacity: on-demand (pay per request) or provisioned (RCUs/WCUs with auto scaling)
  • Eventually consistent reads by default; strongly consistent on request
  • Replicated across 3 AZs; Global Tables for multi-Region active-active
  • Streams, TTL, point-in-time recovery, DAX (in-memory cache), encryption at rest

AWS Global Infrastructure

🌍 Regions and Availability Zones

Regions

  • A physical location containing multiple AZs: us-east-1 N. Virginia, us-east-2 Ohio, eu-west-1 Ireland, ap-southeast-1 Singapore …
  • 30+ Regions, fully independent — a failure or a maintenance event in one cannot affect another
  • Data stays in the Region you choose unless you move it
  • Not every service, instance type or feature is in every Region; prices differ
  • Special Regions: AWS GovCloud (US), China (operated by local partners)

Choosing a Region

  • Compliance — data residency and governance requirements
  • Proximity — latency to your users
  • Feature availability — new services land in a few Regions first
  • Pricing — the same instance costs different amounts in different Regions

Availability Zones

  • One or more discrete data centers with redundant power, networking and cooling
  • Every Region has at least 3 AZs; physically separated (miles apart, distinct flood plains and power grids) but joined by low-latency private fiber
  • Designed so a fire, flood or power loss in one AZ does not affect the others
  • Services like S3, DynamoDB and Lambda are Regional and use multiple AZs for you; EC2, EBS, subnets and RDS instances are zonal — you spread them across AZs
Your Region |- AZ a - data center(s) - your subnet 1, web-1, RDS primary |- AZ b - data center(s) - your subnet 2, web-2, RDS standby +- AZ c - data center(s)

📝 Exam tip: Multi-AZ = high availability within a Region. Multi-Region = disaster recovery and global latency. "AZ" letters map differently per account, so us-east-2a is not the same building for everyone.

⚡ Edge Locations and AWS Global Accelerator

Edge locations / Points of Presence

  • 600+ sites in hundreds of cities — far more than Regions, and much closer to users
  • Home of Amazon CloudFront (content caching), Route 53 (DNS resolution), AWS WAF / Shield (edge protection) and Lambda@Edge / CloudFront Functions
  • Regional edge caches sit between edge locations and your origin for less-popular content
  • You do not launch servers in edge locations; they serve and protect traffic

Extending the Region

  • AWS Local Zones — compute and storage in large metro areas (single-digit ms for gaming, media, AR/VR)
  • AWS Wavelength — inside telecom 5G networks
  • AWS Outposts — AWS racks and services in your data center

AWS Global Accelerator

  • Gives your application two static anycast IP addresses advertised from every edge location
  • User traffic enters the AWS global backbone at the nearest edge, avoiding congested public internet paths
  • Routes to the nearest healthy endpoint (ALB, NLB, EC2, Elastic IP) across Regions; instant failover
  • Works for TCP and UDP, not just HTTP — gaming, VoIP, IoT
CloudFrontGlobal Accelerator
What it doesCaches content at the edgeAccelerates connections to your endpoints
Best forStatic and streaming content, HTTP(S)Dynamic apps, non-HTTP, static IP needs, multi-Region failover
IPsChanging edge IPs via DNS2 fixed anycast IPs

📝 Exam tip: "Static IP addresses for a global TCP/UDP application" → Global Accelerator. "Cache images and video near users" → CloudFront. Both use edge locations.

Billing and Cost Optimization

💵 Understanding AWS Pricing

Three fundamental drivers

  • Compute — per second/hour an instance runs, per ms a function executes
  • Storage — per GB-month stored (plus requests for S3)
  • Data transfer out — per GB leaving AWS to the internet. Inbound is free; transfer between AZs and Regions is charged

Principles

  • Pay-as-you-go — no long-term contracts by default, no termination fees
  • Pay less when you reserve, pay less by using more (tiered S3 pricing), pay less as AWS grows
  • Free Tier: Always free (1M Lambda requests/month, 25 GB DynamoDB), free trials, and a credit-based plan for accounts created after July 2025 (older accounts: 12-months-free, e.g. 750 h t2/t3.micro)

AWS Pricing Calculator (calculator.aws) — estimate a workload before you build; save and share estimates (Lab 8).

✂️ Cost Optimization Strategies

1. Rightsize

  • Match instance type and size to actual CPU/memory/network utilization — most fleets are over-provisioned
  • Use CloudWatch metrics, Compute Optimizer and Trusted Advisor; downsize in steps (t3.large → t3.medium) or change family (Graviton ~20% cheaper)
  • Rightsize storage too: gp2 → gp3, delete unattached volumes and old snapshots, S3 lifecycle to cheaper classes

2. Commit for steady state

  • Cover the baseline with Savings Plans / Reserved Instances; keep the peaks On-Demand or Spot

3. Turn things off

  • Schedule dev/test instances to stop nights and weekends (Instance Scheduler, EventBridge + Lambda) — ~65% savings
  • Delete idle load balancers, NAT gateways, Elastic IPs not attached (they cost money!), forgotten RDS instances

4. Auto Scaling — pay for demand, not for peak

  • EC2 Auto Scaling group: launch template + min/desired/max + scaling policies; replaces unhealthy instances; spreads across AZs
  • Target tracking ("keep average CPU at 50%") · step / simple (CloudWatch alarm thresholds) · scheduled (known peaks) · predictive (ML forecast)
  • Attach to a load balancer so new instances receive traffic automatically
  • Same idea elsewhere: DynamoDB auto scaling, Aurora Serverless, Lambda (scales itself), Application Auto Scaling for ECS
CloudWatch CPU > 70% --> alarm --> ASG adds an instance --> ALB routes traffic to it CloudWatch CPU < 30% --> alarm --> ASG removes an instance min 1 --- desired 2 --- max 4

5. Use managed and serverless services

  • Lambda, Fargate, DynamoDB, S3 — no idle capacity to pay for; less operations time

📝 "Handle variable traffic cost-effectively" → Auto Scaling + ELB. "Reduce cost of a consistently under-utilized instance" → rightsize.

Best Practices and Troubleshooting

🛠️ Building Secure and Reliable Applications on AWS

🔒 Security best practices

  • MFA on root and every user; no root access keys; least-privilege IAM; roles for machines
  • Security groups scoped to exact ports and sources; SSH via Session Manager, not 0.0.0.0/0
  • Encrypt everything at rest (KMS) and in transit (TLS/ACM); keep S3 Block Public Access on unless you mean it
  • Secrets in Secrets Manager or Parameter Store — never in code or user data
  • Turn on CloudTrail (all Regions), GuardDuty, Config; review Trusted Advisor security checks and IAM Access Analyzer
  • Patch on a schedule (Systems Manager Patch Manager); tag every resource

🛡️ Reliability best practices

  • Design for failure — assume any instance, AZ or dependency can fail; no single points of failure
  • Multi-AZ everything — subnets, Auto Scaling groups, ELB, RDS Multi-AZ; multi-Region for DR when the business needs it
  • Stateless servers — sessions in DynamoDB / ElastiCache, files in S3 / EFS, so instances are disposable
  • Decouple with SQS, SNS, EventBridge so a slow component does not take down the rest
  • Automate — infrastructure as code (CloudFormation / CDK), immutable AMIs, CI/CD; humans make typos at 2 a.m.
  • Monitor and alarm — CloudWatch metrics, logs and alarms; test backups and recovery (RTO / RPO) before you need them
Route 53 --> CloudFront + WAF --> ALB (2 AZs) --> Auto Scaling group (stateless web tier) --> RDS Multi-AZ / DynamoDB | +--> ElastiCache +--> S3 (static assets, logs) CloudWatch + CloudTrail + GuardDuty watch it all

🔍 Common Troubleshooting Techniques

"I can't reach my instance / web page"

  1. Is it running and passing both status checks?
  2. Does it have a public IP (or Elastic IP)?
  3. Is the subnet's route table sending 0.0.0.0/0 to an IGW?
  4. Security group: inbound rule for the port from your source?
  5. Network ACL: inbound and outbound allowed, including ephemeral ports 1024–65535?
  6. Is the service listening on the instance (systemctl status httpd, OS firewall)?
  7. Read the system log / user-data output: /var/log/cloud-init-output.log

"Access Denied"

  • Which identity am I? (aws sts get-caller-identity)
  • Is there an explicit Deny anywhere (SCP, permissions boundary, bucket policy)? Deny always wins
  • S3: Block Public Access, bucket policy and IAM policy must all agree
  • Use the IAM Policy Simulator and CloudTrail (errorCode: AccessDenied)
